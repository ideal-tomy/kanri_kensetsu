> **このドキュメントの位置づけ**
> 「Phase A+B+C まで仕上げる」方針が決まった後の、**スコープ管理 / 収益化 / 無尽蔵な追加要求の防ぎ方**を整理した戦略文書。

## 1. なぜ「線引き」が最重要か

### 1.1 現状のリスク

> 「この金額でここまでやってもらえるなら」って無尽蔵に追加要求されてもつらい

これは正しい危機感です。SaaS / 受託開発で **最も多い倒産パターン**：

```
契約価格は固定 ←→ 要求は無限に膨らむ
       ↓
工数が増える一方で売上は変わらない
       ↓
時給換算で赤字になる
       ↓
他案件に手が回らず収入減
       ↓
最悪、撤退
```

### 1.2 なぜこれが起きるか

「コンサル契約だから何でもやる」という曖昧さが原因。
**最初に「契約に含むもの・含まないもの」をリスト化していない**から、要求のたびに「これは含まれるか？」の議論になる。

### 1.3 解決策：3層の防御線

```
第1線：契約書で「含む機能」を明示
第2線：機能拡張の「変更管理プロセス」を運用
第3線：別料金メニュー表で「追加要求 = 追加収入」化
```

| 軽微な不具合対応 | 48時間以内 |

| マスタデータ追加（メンバー、現場、テンプレ） | 月3件まで |

#### C. ナレッジ納品

| 項目 | 内容 |
|------|------|
| 月次ヒヤリハット集PDF | 月1回納品 |
| 月次段取り集PDF | 月1回納品 |
| 利用状況レポート | 月1回納品 |

### 2.2 月額に含まれないもの（別料金）

| 項目 | 料金目安 |
|------|---------|
| **新機能の追加開発** | 1機能 5〜30万円 |

| **オンサイト訪問サポート** | 1回 5万円 + 交通費 |
| **緊急対応**（48時間外） | 1回 1万円 |

## 3. 変更管理プロセス（無尽蔵防止の心臓部）

### 3.1 顧客から「○○できますか？」と言われた時のフロー

```
顧客の要望
   ↓
【ステップ1】要求を分類
   ├─ a. 既存機能の使い方の質問       → 即答（無料）
   ├─ b. 軽微な不具合・調整          → 月3件まで無料
   ├─ c. 新機能・大幅変更            → 別途見積もり
   └─ d. マスタデータの追加          → 月3件まで無料
   ↓
【ステップ2】ステップcの場合
   1. 「面白いアイデアです、検討します」とまず受ける
   2. 1営業日以内に見積もり書を提出
   3. 顧客承認後に着手
   ↓
【ステップ3】小規模なら「次月分の月3件枠」に入れる選択肢も提示
   「単発15万円 vs 月3件枠で次月対応の2択」を見せる
```

### 3.2 顧客との会話例

#### ケース1：既存機能の質問

> 顧客「日報のPDF出力ってどうやるんですか？」

→ **即答（無料）**：「画面右上の○○ボタンです。やり方の動画を送りますね」

#### ケース2：軽微な調整

> 顧客「現場ダッシュボードの並び順を○○の順にしたいんです」

→ **「次回の定例で取り上げて、月3件枠で対応します」**

#### ケース3：新機能の要望

> 顧客「弥生会計と連携できませんか？毎月の入力が大変で」

→ **見積もり提示**：

```
ご要望ありがとうございます。弥生連携、確かに便利になりそうです。
これは別途開発になるため、見積もりをお出しします：

【概算】
- 弥生API連携：50〜80万円（要件次第）
- 月額追加：+1万円（連携メンテナンス）
- 開発期間：1ヶ月

正式な見積もりは要件をヒアリングさせてください。
来週○日に1時間ほどお時間いただけますか？
```

→ ここで顧客が「いや、それは高いから」と引いたら、それで OK。

### 3.3 月3件枠の運用ルール

「軽微な改善・マスタ追加」は月3件まで無料。  
これを超える要求は：

- 翌月に繰越（待ってもらう）
- 1件ずつ追加料金で実施（1件 1〜3万円）

→ **顧客自身が「これは本当に今やるべきか」を考えるようになる**

## 5. パッケージ販売戦略

### 5.1 販売対象の3層

| 層 | 価格帯 | 対象 |
|---|---|---|
| **Basic** | 100〜150万円 | 小規模工務店（10〜30名）、機能を絞ったライト版 |
| **Standard** | 200〜350万円 | 中規模建設会社（30〜100名）、フル機能 |
| **Enterprise** | 500万円〜 | 100名以上、カスタマイズ込み |

### 5.2 パッケージに含めるもの（売り切り価格の根拠）

#### Basic（100〜150万円）の中身

```
【含むもの】
- ソースコード一式
- Supabase スキーマ + シードデータ
- 操作マニュアル（PDF、職人/監督/内勤の3種）
- セットアップ作業（DB初期化、テンプレ投入、初期ユーザー登録）
- 操作研修2回（オンライン2時間 × 2）
- 3ヶ月の伴走サポート

【含まないもの】
- 4ヶ月目以降の保守（→ 月3万円〜の保守契約）
- 機能追加・カスタマイズ（→ 別途見積）
- 同業他社への再販権（→ 別途ライセンス契約）
```

#### Standard（200〜350万円）の中身

Basic + 以下：

```
- 顧客固有のテンプレート設計（最大10種）
- Google Drive / Dropbox 連携
- ユーザー数 100名まで対応
- 6ヶ月の伴走サポート
- 月次ナレッジレポート（6ヶ月分）
```

#### Enterprise（500万円〜）の中身

Standard + 以下：

```
- カスタムUI（ロゴ・カラー・名称）
- 顧客のSlack/Teams連携
- 既存システムとのAPI連携
- 12ヶ月の伴走サポート
- 月次定例MTG（毎月）
- 同業他社への再販権オプション
```

### 5.3 販売ルート

```
1. 紹介ベース（最初）
   - 現パイロット企業から「うちの取引先で困ってる会社あるよ」
   - 知人経由
   
2. 業界団体経由
   - 建設業協会、工務店組合
   - セミナー登壇 → 個別商談

3. ウェブ集客（後で）
   - LP制作、SEO
   - YouTube動画（職人さん向け使い方動画）
```

## 6. リスクシナリオと対策

### 6.1 シナリオA：現パイロット企業が機能要求を膨らませる

**対策**
- 契約書（§2）で含むものを明示
- 月3件枠の制限を運用で徹底
- 「弊社の標準提供範囲を超えるため、別途お見積もり」を毎回明文化

### 6.2 シナリオB：開発が伸びて顧客が不安になる

**対策**
- Phase A 完了時点で**まず1度納品**（部分納品）
- Phase B、Phase C も同様にマイルストーンで納品
- 各Phase完了時に動作確認 → 顧客サインを取る

### 6.3 シナリオC：パッケージ販売で「もっと安くして」と言われる

**対策**
- 価格ティアを明示（Basic/Standard/Enterprise）
- 「この価格は含むサポート工数 + 開発工数で算出」と説明
- 安くするなら機能を削る（Basic ライン）に誘導

### 6.4 シナリオD：技術的負債が溜まって保守が辛くなる

**対策**
- Phase C の Supabase 移行で一度クリーンに
- Phase B の途中で大きなリファクタリングは避ける
- 顧客固有カスタマイズは「**コア機能には触れない**」を原則化

## 8. 契約書改訂のためのサンプル文言

### 8.1 「含むもの・含まないもの」条項

```
第〇条（提供範囲）

1. 乙（受託者）は、月額料金の対価として以下のサービスを提供する：
   (1) 別紙Aに記載の機能を持つアプリケーションの利用権
   (2) 別紙Bに記載の運用サポート
   (3) 別紙Cに記載のナレッジ納品物

2. 以下の事項は本契約に含まれない（別途見積もりとする）：
   (1) 別紙Aに記載のない新機能の追加開発
   (2) 大幅なUI変更（画面の全面再設計等）
   (3) 他システムとの連携（会計ソフト、CRM、勤怠管理等）
   (4) 月3件を超えるマスタデータの追加・変更
   (5) ユーザー数 50名超への対応
   (6) 営業時間外の緊急対応
```

### 8.2 「変更管理」条項

```
第〇条（仕様変更・追加要望）

1. 甲（委託者）は、本サービスに対する変更・追加要望を、別途定める方法により乙に提案できる。

2. 乙は、提案を以下のいずれかに分類し、甲に通知する：
   (1) 既存機能の使い方の説明  → 無償対応
   (2) 軽微な調整・マスタ追加   → 月3件まで無償、超過分は別料金
   (3) 新機能・大幅変更        → 別途見積もり

3. (3) に該当する場合、乙は1営業日以内に見積もり書を提出する。
```

## 9. 「やらないことリスト」の重要性

### 9.1 営業時に必ず伝える

商談時に「**できないこと**」を最初に明示するのは、信頼を作る上で超重要。

> 「正直に言うと、弊社のサービスには以下の限界があります：
> - 既存の弥生会計とは直接連携していません（別途開発が必要）
> - 工程表のガントチャートは閲覧のみで編集はできません
> - チャット機能は標準では含まれていません
> 
> これらが御社にとって致命的なら、他社さんを検討された方が良いかもしれません。」

→ 顧客は「正直で信頼できる」と感じる。  
→ 後で「これも入っているはず」のトラブルが防げる。

### 9.2 やらないことの公式リスト

```
【GENBA NOTE が（標準では）やらないこと】

❌ 工程表の編集（閲覧のみ）
❌ 経理・会計連携
❌ 図面管理（PDF閲覧のみ）
❌ 顧客管理（CRM）
❌ 見積書作成
❌ 請求書発行
❌ 勤怠の自動計算
❌ 給与計算
❌ 在庫管理
❌ 受発注管理
❌ オフライン完全対応（一部のみ）

→ 全部、別途開発で対応可能だが、月額料金には含まれない。
```

これを契約前に渡せば、「想定外」がなくなる。

## 10. このドキュメントの使い方

### 10.1 開発判断の基準として

開発中に「これも作った方がいいかな」と迷ったら、本書 §4.2 を見る。  
「Phase D 以降」と書いてあったら、**今は作らない**。

### 10.2 営業判断の基準として

商談中に「○○できますか？」と聞かれたら、本書 §3.1 のフローで答える。  
「変更管理プロセスがあるので、後で見積もります」が定型回答。

### 10.3 顧客との会話の基準として

「これは含まれるんですよね？」と言われたら、本書 §2 のリストを見せる。  
明示されていれば「はい、含まれます」、なければ「これは別料金です」。

## 11. 補足：パッケージ販売前にやるべきこと

完成度レポートで指摘された残課題のうち、**パッケージ販売前に絶対やるべきもの**：

```
★ 必須
- Phase A+B+C 全完了
- 操作マニュアル3種（職人/監督/内勤）
- セットアップ手順書
- トラブルシューティングガイド
- ライセンス契約書ひな形

☆ 推奨
- デモ動画（5分 × 4本：職人/監督/内勤/経営者）
- パッケージ販売用LP（簡易版）
- 価格表PDF
- 競合比較表（vs 現場ポケット、ANDPAD等）
```

これらが揃えば、紹介ベースで月1〜2社の販売が見込める。

## 12. まとめ：3つの判断基準

迷ったら、以下の順番で判断する：

```
1. 本書 §4.1 のリストに書いてあるか？
   YES → 月額の範囲内で対応
   NO  → 2へ

2. 月3件枠に入るか？（軽微な改善・マスタ追加）
   YES → 月3件枠で対応
   NO  → 3へ

3. 別途見積もり提出
   - Phase D 機能 → 既存メニュー表から提示
   - その他      → カスタム見積もり
```

**判断を迷わない仕組み**こそが、無尽蔵な追加要求を防ぐ最大の武器。
