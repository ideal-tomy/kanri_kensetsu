## 5. リテラシーの低い現場・経営者のためのUX改善提案

### 5-A 経営者ダッシュボードの「一目でわかる」設計

**現状の問題**: 現在の`/admin`は4つの統計カード（作業員数・案件数・請求見込み・アラート数）があるが、「全現場の健康状態」が一画面で分からない。数字を読み解く必要がある。

**提案 ― 全現場ステータスカード**

```
[現場名]    A邸新築
進捗 ████████░░ 42%  ← 計画進捗52%より▼10% 遅れ
人員 今日4名
写真 本日3枚投稿済み

[現場名]    Bビル改修
進捗 ██████████ 68%  ← 計画どおり ✓
人員 今日3名
写真 本日5枚投稿済み
```

実装イメージ:
- `state.sites` + `state.tasks` + `state.photoReports` + `state.assignments` を組み合わせて1枚のカードに集約
- 進捗バーは「計画値vs実績値」で色分け（遅延=オレンジ、順調=緑）
- 写真・日報の当日実績カウントを小さく表示
- タップで案件詳細へ

---

### 5-B 人員配置の「変更しやすい」設計

**現状の問題**: `WeekCalendar`は閲覧のみ。急な欠勤が起きたとき、内勤が何もできない。

**提案 ― セルタップで変更モーダル**

```
月曜日 A邸新築 セルをタップ
  ↓
モーダル表示
  ┌─────────────────────────┐
  │ A邸新築 月曜日          │
  │                         │
  │ 現在: 田中さん（日勤）  │
  │ [変更する] [欠勤にする] │
  └─────────────────────────┘
  ↓
変更先を選択:
  [Bビル改修に移動] [Cマンションに移動]
```

実装イメージ:
- WeekCalendarのセルに`onClick`ハンドラーを追加
- 小さいモーダル（Drawer）で「誰を追加/変更/削除」の3操作
- `applyAssignmentChange`（prototype-store）を呼ぶ
- 変更があったセルは赤枠（実装済みスタイル`ring-2 ring-red-500`が既にある）

---

### 5-C 現場登録フォームの「シンプル設計」

**使用説明§2.2に必要な情報**があるが、フォームがない。  
リテラシーが低い利用者向けには、入力項目を最小限に絞ることが重要。

**提案 ― 4ステップウィザード**

```
STEP 1: 現場の名前と住所
  ┌─────────────────┐
  │ 現場名（必須）   │
  │ A邸新築工事     │
  ├─────────────────┤
  │ 住所（任意）    │
  │ 札幌市...       │
  └─────────────────┘

STEP 2: 工期
  ┌─────────────┬──────────────┐
  │ 着工日      │ 完工予定日  │
  │ 2026/05/10  │ 2026/08/31  │
  └─────────────┴──────────────┘

STEP 3: 担当者（誰を配置するか）
  ☑ 田中さん（日勤）
  ☑ 佐藤さん（日勤）
  □ 鈴木さん
  
STEP 4: 確認
  → 「この現場を作成する」ボタン
```

**ポイント**: 一度に全情報を入力させない。後から追加できるようにする。  
特に「住所・工事種別・元請情報」は後から編集可能にして、初回登録のハードルを下げる。

---

### 5-D 監督の写真確認画面

**現状**: プレースホルダ。  
**使用説明での位置づけ**: 監督が「定期的にチェック」する最重要習慣。

**提案 ― カテゴリ別シンプル2カラム**

```
[定例報告] ───── [進捗報告]

最新5件の写真サムネイル（縦長スクロール）

各写真に:
  ・投稿時刻
  ・投稿者名
  ・タイトル（進捗のみ）
  ・補足メモ
```

実装上のポイント:
- `LivePhotoGalleryGrid`コンポーネントがすでに存在（Supabase Realtime対応済み）
- `getPhotoReportsForUser(supervisorUser)` を Server Component で呼ぶだけで実装可能
- 追加工数: 1〜2時間程度

---

### 5-E ログインの「あいことば」化（現場向け）

**現状**: 会社コード+名前入力。現場の職人にとってはすでにわかりやすい設計。  
**改善余地**: 「ワンタップログイン」として仮アカウントボタンがあるが、本番ではPINコード（4桁）ログインが職人には最も楽。

**提案**: パスワード欄にPINモード（`inputmode="numeric"`、4桁表示）を追加し、キーボードを数字パッドにする。スマートフォンで片手でも入力しやすい。

## 7. データモデルの現状ギャップ（Supabase移行時の注意点）

### 二重データ問題

現在、アプリには2つの独立したデータ源泉がある。

| 層 | 場所 | 使用箇所 |
|---|---|---|
| 静的モック | `src/data/mock/*.ts` | adminの大部分（projects, workers, assignments等） |
| 動的インメモリ | `src/lib/prototype-store.ts` | worker/supervisorページ、一部admin |

**Supabase移行時には統一が必要**。特に:

| mock | prototype-store | 違い |
|---|---|---|
| `projects`（id: p1, p2...） | `sites`（id: site-1, site-2...） | 概念・IDが別 |
| `assignments`（workerId, aiScore） | `assignments`（userName, siteId） | スキーマが別 |
| `reportPhotos`（renamedFileName, aiConfidence） | `photoReports`（category, title） | 型が別 |

移行時は使用説明§3のDB設計（`projects → sites`の親子構造）に統一する。
